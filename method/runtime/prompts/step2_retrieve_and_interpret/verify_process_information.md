Review a proposed process selection against the analyst's request. Report specific, grounded disagreements and verify the evidence for each requirement. A later step resolves remaining uncertainty.

# Input (runtime_data)
- original_request: the analyst's question (the only task).
- request_interpretation: an independent parse of the request (case_requirement, activity_scope, activity_requirements R1..Rn, process_focus). Neither it nor the selection is authoritative; compare them with the request.
- selection: the proposal: entity_type {name, instance_definition}, mode (explicit or implicit), focus, ids, activities (id, name, meaning, description, dictionary_evidence), classifications (implicit focus only: INCLUDE / EXCLUDE / UNCERTAIN per activity).
- retrieved_evidence: literal public dictionary, business-rule and event-semantic text, marked candidate_only. Use it to resolve synonyms and codes. A retrieved candidate is not an approved selection. Absence from retrieval is not proof that an event does not exist.

# What to check
1. case_mismatch (target: the selected ET ID). Compare the actual unit and the applied case_scope. A scoped role can narrow a more general entity label and description. Compare the requested case noun and unit with entity_type.name and instance_definition. "each", "every" and "per" describe grouping; a type that represents one instance is exactly what grouping needs. Report only if the request denotes a different entity or a different unit.
2. Explicit mode only:
   - unmatched (target: one exact requirement span): a requested activity that no selected activity expresses. Compare each requirement with every selected activity's meaning, description and dictionary_evidence, including paraphrases and noun/verb forms.
   - unrequested (target: one selected definition ID): a selected activity that no requirement expresses. Before reporting, check every requirement phrase against it. An event label need not repeat the case noun. A case or grouping phrase is not an activity requirement. If two selected activities both express one requirement, neither is unrequested.
3. Implicit mode only: never report unmatched or unrequested for named activities, and never invent activities.
   - focus_conflict (target: a classified ID): the classification clearly contradicts the focus meaning (an INCLUDE that is not part of the focus, or an EXCLUDE that clearly is).
   - uncertain (target: a classified ID): report every activity classified UNCERTAIN.
   - Whole history with no focus: nothing to report except case_mismatch.

# Explicit requirement review
When selection.activities is empty, read the records for selection.ids from activity_review.candidates. A missing code_meaning or meaning field may repeat the name.
When activity_review.scope_verification is true, each requirement review must contain candidate_decisions for every offered card exactly once. Each judgment contains {event_definition_id, decision, span, quote}. Use include for a member required by the request, exclude for a known non-member, and unresolved when the evidence cannot decide. Use a literal request span and copy the supporting wording from that card's dictionary evidence, source context (including source_context_by_table), or, if neither is supplied, its meaning or name. A verified occurrence can be required even when it was absent from the initial selection. Explicitly consider documented peer codes and lifecycle boundaries. A candidate with a matching meaning but no usable attribution should still be diagnosed as a gap.
When activity_review is present, return differences for case or mode only. In requirement_reviews, review every ID in activity_review.requirements exactly once. Do not review IDs that are absent from this list. Check the raw request for context and the activity's qualifiers, and read activity_review.candidates, including definitions outside the proposed selection and ones lacking case attribution. A direct_case_mapping anchors an event on the case itself or a child that identifies it, so a departure-phase event with this mapping does not need a separate leg path.
- For each item, independently set reviewed_coverage and reviewed_granularity from the original request and the requirement span. A plural occurrence family may require multiple distinct occurrences even when the parser treated a named endpoint as the only occurrence. Retain canonical activity distinctions while verifying every relevant occurrence. An unrestricted lifecycle request can cover multiple canonical activities. Use the stable requirement ID and list every complementary definition needed to satisfy the reviewed span. Include an exact match outside the initial selection when the evidence supports it. Multiple documented codes or phases are members of the family, not ambiguous alternatives. For distinct granularity, verify each needed type. For coarse granularity, verify the full requested scope using selected canonical definitions. A generic record over the same occurrence rows is an alternative representation of its specializations. Treat case_scope as the active restriction on the ET population. A full ET definition can mention other roles when its supplied case_scope limits the output to the requested role. Report a semantic match if a definition describes the requested occurrence and uses the correct time. Preserve all genuinely plausible same-occurrence candidates if ambiguous. Use time_mismatch for an otherwise relevant definition using a different time, such as an estimate, message receipt, start instead of completion, or a generic posting clock. Use missing with an empty ID list when no definition captures that occurrence in the supplied EEG evidence. A generic code family does not implement a specific code or phase.
- Interpret the activity scope and the unit of an occurrence independently of Case grouping. If the request specifies milestones at a particular business level, check what one record represents for each proposed ED. A record of an individual participant's action does not become a lifecycle milestone for a whole operation merely because a valid path attributes it to that operation. Keep individual actions when the stated process or analysis asks for those actions. Apply a stated activity-level restriction to intermediate milestones as well as named endpoints. When omitting an initial candidate for this reason, cite the exact scope phrase and identify the ED's documented occurrence unit.
- A plural group of milestones can span distinct physical EDs. If a request gives the first and last events as boundaries, examine intermediate events and each stated direction or role. For example, "receipt and dispatch milestones from truck arrival to yard exit" can include unloading completed and loading completed between the endpoints. Treat the documented complementary occurrences as coverage "all". A single named phase, an explicit exclusion, or an explicit limit can justify narrower coverage. Apply shared modifiers to every conjunct they govern. When two requirements cite the same clause, use each requirement's meaning to tell them apart.
- activity_review.initial_proposals lists the initial EDs for each pending requirement. Reconcile every offered initial ED with the original request. If exclusions is in the response schema, return one entry for every initial ED omitted from event_definition_ids and [] if none is omitted. Each exclusion contains event_definition_id, kind, span, and reason. Copy a literal span that supports excluding that specific occurrence. Use different_occurrence, wrong_phase, wrong_role, or duplicate_occurrence. For a duplicate identify the retained covering ED and explain the common physical occurrence. A singular shorthand in the parse, a preferred endpoint, or terse evidence cannot justify dropping a complementary ED. Use ambiguous when the evidence leaves competing interpretations unresolved.
- activity_review.revised_proposals may provide a new proposal for a pending item. Validate it independently against original_request and the EEG. Account for omitted EDs from the original and revised proposals. When case_is_locked is true, keep the previously verified case and return differences []. Verified requirements will be absent from activity_review.requirements.
- Even if a matching definition has no valid case path, list its ID so the controller can diagnose attribution separately. Use source_attribution_gap=true only if there is evidence that the relevant source events require a role path that the EEG does not provide. Use documented_sources to identify a code for the actual requested occurrence even if no ED has that code. When the identified source has no passing path for the required role in its candidate cards, report source_attribution_gap=true alongside missing or time_mismatch. A documented code is evidence of the source meaning and does not establish a definition or a case path. Do not infer a second gap just from an absent definition.
- Confirm a case only when its instance definition matches the unit the analyst asks for. Report case_mismatch if it differs or the evidence cannot confirm it.
- Give a concrete reason. Copy only verbatim text if quoting the request or evidence.

When required_case_scope_id is in the response schema, independently read the analyst's case constraint and select the matching documented option from case_scope_options. Use the empty string when that case role is unrestricted. Evaluate the case noun separately from the selected subset; the controller reconciles a discrepancy in scope.

When role_path_choices is in each activity review, use entries {event_definition_id,path_id} to ground role-qualified attribution. Each event with competing role_projections needs the one path that corresponds to its role in the requested process. A family can contain members in different roles. Consult the event meaning, source context, and quoted definitions of both reference roles. A passing physical path does not establish that its role is the intended one. Leave a choice empty when the intended role cannot be justified. For example, in "sent to received for each transfer", a dispatch record follows the source account and a receipt follows the destination account.
